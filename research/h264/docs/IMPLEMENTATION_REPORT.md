# H.264 / MP4 Smart Rendering：实现与测试报告

交付版本 0.1.0 · 2026 年 10 月 27 日 · C++20 / CMake / MSVC / FFmpeg 8.1

## 1. 实际交付与结论

本次实现了可编译的 C++ CLI，并在本地生成 Windows x64 可执行程序完成测试。仓库收录源码、依赖获取脚本、自动测试、报告、原始测试视频与结果，不收录编译后的程序或 DLL。程序直接使用 FFmpeg 库处理视频，运行时不启动 ffmpeg 命令行进程。音频不处理，输出只包含视频。

实现选择了一条较小但完整的路线：**只从真实 IDR 开始恢复压缩包复制，不完整的 IDR 区间重新编码；用 FFmpeg 负责参数集承载和 MP4 封装。** 因此不必自行重写 POC、frame_num、MMCO 或 slice header，也不必为新编码器固定设置 `sps-id=3`。

这项简化有明确代价：长期没有 IDR 的 Open GOP 素材可能需要重编码整个选区。这不是“任意素材都只改几帧”的算法。报告下文量化了这一限制。

最终二进制的验收结果：

| 验证项 | 结果 |
| --- | --- |
| 13 类素材 × 10 种剪辑 × 2 种参数集承载 | 260/260 通过 |
| 8-bit / 10-bit 无损回退 × 2 种承载 | 4/4 通过 |
| 非法参数和不支持输入的拒绝测试 | 11/11 达到预期 |
| 删除原参数集恢复的破坏性对照 | 1/1 成功检出损坏 |
| 中文路径、音频轨在前、随机访问和坏 NAL | 5/5 通过 |
| CTest 启动检查 | 1/1 通过 |

正常闭合 GOP 示例：240 帧输入保留 `[13,227)`，输出 **214 帧，192 帧复制、22 帧重编码**。复制部分的 VCL NAL SHA-256 和解码像素均与输入一致。这里的“无损复制”不包括容器字节、NAL 长度前缀或插入的参数集。

结果没有支持“设置不同 SPS ID 就能解决一切”的判断：正常有损边界可以安全复用 ID；而探索测试中的无损/有损混合问题，更换 ID 后仍然存在。当前版本对后一种情况采用显式全选区无损编码回退。

## 2. 范围与术语

本报告讨论 H.264/AVC 视频、MP4 容器；不讨论音频拼接、字幕或杜比技术。用户输入是显示帧序号，不是秒数。`--keep A:B` 表示 `[A,B)`，多个保留区间顺序连接，去掉被删除的时间段。

| 术语 | 对本实现的意义 |
| --- | --- |
| SPS / PPS | 描述切片如何解码的配置；不是可以任意替换的“文件头” |
| SPS ID / PPS ID | 参数集索引；新旧流编号相同不必然错误，定义必须在正确时机生效 |
| IDR | 重置参考关系的随机访问点；本实现恢复复制的依据 |
| 普通 I 帧 | 自身为帧内编码，不保证其周边帧不引用此前画面 |
| 容器 key flag | 解复用器标记，不作为真实 IDR 的替代 |
| AVCC / Annex B | 长度前缀与起始码两种 NAL 封装；转换本身不重编码画面 |
| avcC | MP4 中的 AVC 配置记录，可包含多组 SPS/PPS |
| avc1 / avc3 | 本实现两种参数集承载方案所用的 sample entry |
| PTS / DTS | 显示时间与解码时间，含 B 帧时不能混用 |

H.264 本身不使用 HEVC 的 VPS、CRA 结构，本次没有引入这些处理。IDR 与参数集的概念可参见 [RFC 6184 §4.1](https://www.rfc-editor.org/rfc/rfc6184.html#section-4.1)；其中对参数集更新的说明也表明，关键是定义与使用时机的同步，而非编号必须永久不同。该 RFC 是 RTP 文档，此处只引用 H.264 概念，不把它当成 MP4 封装规范。

## 3. 为什么采用这个边界策略

把新编码画面和原压缩画面放进一条流，要分别解决三个问题：原画面的参考依赖是否完整；解码时是否得到与切片匹配的参数集；输出容器是否准确表达时间和配置切换。仅解决其中一项仍可能花屏、错帧或错时长。

程序先解复用并扫描全部视频样本，记录文件位置、大小、PTS、DTS、duration 和真实 IDR。最小 NAL 检查只解析长度、类型和 `first_mb_in_slice`，不建立完整 H.264 语法树。多 slice 的一帧可以接收，多幅图像合并在一个样本、扩展编码和数据分区 NAL 则拒绝。

随后按 PTS 建立显示顺序，并按实际 IDR 划分区间。对于每个保留区间：完整覆盖的 IDR 区间执行复制；头部或尾部不完整的区间，解码到所需末帧，并只把选中的画面交给新编码器。

例如 IDR 每 24 帧出现一次：

```text
源显示帧：  [0......23][24......47] ... [192.....215][216.....239]
保留范围：          13----------------------------------226
输出行为：          编码11帧 | 复制24..215共192帧 | 编码11帧
```

尾部必须同样处理。B 帧可能依赖剪切终点之后、但在解码顺序中提前出现的参考画面；直接用时间参数截断压缩包，不等于精确保留指定显示帧。

重编码单元使用独立 x264 上下文，closed GOP、B=0，从 IDR 开始。较长单元内部仍可生成其他 IDR。复制单元保留原解码顺序。这样新旧单元之间无需继续同一套参考图像状态，也无需重编号 POC/frame_num。

如果一个 Open GOP 文件只有开头一个 IDR，整个文件就是一个区间。完整保留可以直接复制；内部任意截取则重编码所选画面。高级项目解析 leading pictures、参考列表或重写 POC，是为了减少这种重编码量，有实际用途。

## 4. 参数集：需要管理，但不一定要改 ID

### 4.1 为什么不能直接给新切片套旧 SPS/PPS

新编码器可能选择不同的参考帧数、熵编码方式、POC 表达、帧号位宽、变换方式等。切片按新配置编码，强行声明成旧配置会让解码器错误解释后续比特。即使尺寸、码率、profile 名称相近，也不能据此认定配置兼容。

沿用旧参数集并非理论上不可能：必须让新编码器生成真正遵守旧参数集的语法，或者严格证明新旧相关字段可互换。本版不让 x264 承担这种“精确复现任意来源 SPS/PPS”的约束，而是保留它实际生成的配置。

### 4.2 默认方案：avc3 与带内参数集

新编码部分由 x264 输出自己的 SPS/PPS；复制部分在 IDR 前恢复源 SPS/PPS。实现为每个复制单元创建新的 `h264_mp4toannexb` BSF，让它基于源 avcC 注入所需配置。最后交给 MP4 muxer 转成长度前缀 NAL，标记为 avc3。

因此可以发生“源 ID 0 → 新 ID 0 → 源 ID 0”的切换，只要相应定义在正确的 IDR 前到达。程序没有修改 slice header，也没有固定 `sps-id`。FFmpeg 的现成 BSF 已包含 IDR 前补入参数集的处理，见 [h264_mp4toannexb.c](https://github.com/FFmpeg/FFmpeg/blob/n8.1/libavcodec/bsf/h264_mp4toannexb.c#L353-L366)。

该方案的必要工作是**恢复定义**，不是创造新编号。最终矩阵中的源 `sps-id=0` 和 `sps-id=3` 均通过，两种输入都与新编码器的默认编号组合测试。

### 4.3 对照方案：avc1 与多个 sample description

`--ps-mode stsd` 不要求带内切换，而是将每个单元的配置通过 `AV_PKT_DATA_NEW_EXTRADATA` 交给 FFmpeg 8.1 movmuxer，由 muxer 建立/选择 sample description，并让样本块关联正确的条目。复制和编码配置分开表达，同样不需要改 ID。

实测普通混合输出的 stsd 有 2 个条目；avc3 路线为 1 个条目。两种路线的线性解码、复制像素、时间戳与 IDR seek 均通过。实现依据是 [movenc.c 的配置变更处理](https://github.com/FFmpeg/FFmpeg/blob/n8.1/libavformat/movenc.c#L6396-L6454)。它依赖具体 FFmpeg 版本，不能直接推广到任意旧构建或任意播放器。

### 4.4 需要纠正的一点

此前参考项目文档中有“avcC 只能保存一组参数集”的概括，不能据此推断 MP4 必须改写原 SPS 或只能采用 avc3。avcC 有 SPS/PPS 数量和数组；MP4 也有多个 sample description 的表达方式。FFmpeg 的 [avc.c](https://github.com/FFmpeg/FFmpeg/blob/n8.1/libavformat/avc.c#L60-L92) 就遍历多组参数集。更准确的问题是：**同一条轨道如何把样本与当时有效的配置正确关联，以及播放器是否支持这种关联方式。**

## 5. 时间轴与 MP4 的处理

本版不采用“前段减去一个平均帧时长”“遇到 DTS 回退就加 1”或凭片段文件时长猜测连接点的办法。

设输入显示边界为 `t[0..N]`。前 N 项是排序后的 PTS，末项由最后一帧 PTS 加其正时长得到。计划单元 `[a,b)` 的输出起点为 `O`：

```text
输出 PTS = O + 原始 PTS - t[a]
单元时长 = t[b] - t[a]
下一单元起点 = O + 单元时长
```

为保留原包的解码顺序，第 j 个解码包分配递增时隙 `s[j]=O+t[a+j]-t[a]`。扫描全部复制单元，取 `D=max(0, s[j]-输出PTS[j])`，再令输出 `DTS=s[j]-D`。编码单元没有 B 帧，沿用这套时隙。由此 DTS 严格递增且不晚于 PTS，各单元之间也连续衔接。

初始 DTS 可以为负；MP4 muxer 通过 ctts 和 edit list 表达显示时间。输出显示从零开始，保留帧之间的显示间隔使用原始整数 tick，不靠平均 FPS 推算，所以支持本次 VFR 素材。

这重建的是**容器层**解码时间。它不等于证明原码流的 HRD/CPB 计时在剪切后仍然满足规范；严格 HRD 工作流不在本版保证范围内。普通文件播放测试通过，不能替代流缓冲合规性分析。

MP4 的解析、写 stts/ctts/stsc/stsd、NAL 封装转换、edit list 和 faststart 均使用 FFmpeg。自写部分只计算剪辑结果需要的关系，未自行编写 MP4 muxer。

## 6. 各项目中哪些处理值得采用

比较基于 2026-10-25 下载的固定源码快照，具体 SHA 见 [source-manifest.json](evidence/source-manifest.json)。以下是本次限定范围内的判断，不是对各项目整体质量的排序。

| 项目 | 有价值的处理 | 本版取舍 |
| --- | --- | --- |
| LosslessCut | 利用 FFmpeg 编码、复制和拼接，编排成本低；关注时间基匹配 | 采用依赖 FFmpeg 的方向，改为直接调用库，并以明确的显示帧计划同时处理首尾 |
| skeskinen/smartcut | 包级复制与边界编解码，便于在同一输出流组织处理 | 采用整体架构；固定 `sps-id=3` 不是本版必需条件 |
| DeepRegular/SmartCut | 复制/编码计划、leading-reference 分析、逐帧验收和容器适配 | 采用计划与验证思想；更激进的依赖分析不纳入本版，以扩大编码区间换取更小核心 |
| MediaMolder | 明确区分 NAL framing、参数集布局与时间戳；按输入编码器选择策略 | 这些问题都保留，但把 framing 与配置封装尽量交给 FFmpeg；不实现 open-GOP POC 改写 |
| VidCutter | 首、中、尾三部分处理比仅处理开头完整 | 采用两端都处理的原则；不需要临时片段文件与二次 concat |
| avcut | GOP 缓存后判定复制或编码，强调边界上下文 | 采用区间判定；用文件位置索引减少整段压缩包缓存 |
| VirtualDub | 调度器明确区分可直接复制帧与需压缩帧 | 采用调度思想；AVI/VFW 格式和编码器协商不适用于此处 |

对应源码入口：[LosslessCut 剪辑编排](https://github.com/mifi/lossless-cut/blob/3ef357d88d51d8a2a36e5bf3c041b3a269bfbc5a/src/renderer/src/hooks/useFfmpegOperations.ts#L617-L733)、[skeskinen 编码配置](https://github.com/skeskinen/smartcut/blob/73821ea01c29a4dca81a8865ef7d348d04bb0810/smartcut/video_cutter.py#L305-L310)、[DeepRegular planner](https://github.com/DeepRegular/SmartCut/blob/84252659110ad34e1af02689f3013badc1561a1e/rust/crates/core/src/plan.rs#L624)、[MediaMolder smartcopy](https://github.com/MediaMolder/mediamolder/blob/9e51f8f761588e2e3c5ef87e9f11dfd5c091ac58/docs/smartcopy.md)、[VidCutter 后端](https://github.com/ozmartian/vidcutter/blob/62d9b0657fd841c74a8d5bb184512ddaddacbce2/vidcutter/libs/videoservice.py#L261)、[avcut GOP 处理](https://github.com/anyc/avcut/blob/7704c26c95a4540a43e5c9ce9c6470595a78eddc/avcut.c#L248)、[VirtualDub 调度](https://github.com/fishman/virtualdub/blob/388a9e98ff08b9b546e4c053c3781a760f5ff976/VirtualDub/source/DubProcessVideo.cpp#L345)。

### 6.1 哪些是必要问题，哪些是可选实现

| 处理 | 判断 | 原因与本版替代 |
| --- | --- | --- |
| 判断参考依赖是否闭合 | 必要 | 本版用真实 IDR 保守判定；不能拿 key flag 替代 |
| 保证参数集及时到达并匹配切片 | 必要 | 消融实验证明不恢复源配置会损坏复制部分 |
| 总是更换 SPS/PPS ID | 非普遍必要 | 同 ID 的 avc3 切换和分开 stsd 均通过；如采用单一 avcC 多配置共存，则分配不冲突 ID 很有用 |
| 固定新 SPS ID 为 3 | 只是启发式 | 源文件也可能使用 3；不能替代配置管理 |
| 强制新旧 SPS/PPS 字节相同 | 非必要且可能错误 | 独立编码区间可使用不同但正确的配置 |
| Annex B / AVCC 转换 | 必要问题 | 本版使用 FFmpeg BSF/muxer，无需重复实现复杂转换 |
| POC/frame_num/MMCO 改写 | 本版不需要 | 只在 IDR 恢复复制；若要在非 IDR Open GOP 内衔接，它们可能成为必要工作 |
| 精确首尾帧和有理数时间轴 | 必要 | B 帧和 VFR 使“按秒截一段再拼接”容易出现偏差 |
| 新编码 GOP 也使用 B 帧 | 可选优化 | B=0 简化接缝时间轴，但压缩效率较低 |
| 把新码率设为源码率的某个倍数 | 不是兼容性证明 | 码率不描述切片语法；本版用 CRF 管质量，并实测图像误差 |
| 逐帧解码与压缩数据双重验证 | 必要的验收手段 | 解码无报错也曾发生像素不一致 |
| 自己写 MP4 box、临时文件 concat | 本版不需要 | FFmpeg 公开 API 已提供所需能力 |

因此，“LosslessCut 没有改 SPS ID，所以一定设计错误”不成立；“别的项目做的码流处理都是过度设计”也不成立。它们的范围、容器约束、播放器目标和最少重编码目标不同。应判断问题有没有被某一层可靠解决，而不是按自写代码数量评判。

FFmpeg concat demuxer 本身会在适当条件下自动接入 `h264_mp4toannexb`，调用者没有显式写 PS 逻辑，也可能获得参数集补入行为。可见 [concatdec.c](https://github.com/FFmpeg/FFmpeg/blob/n8.1/libavformat/concatdec.c#L188-L225)。但这不负责证明任意剪切点的参考安全性和显示帧边界正确性。

### 6.2 issue 能说明什么

此前调研中的花屏、少帧、多帧、拼接失败，应分别定位到依赖分析、参数集、framing、时间轴或编码参数约束；单看症状无法确定唯一根因。

| 公开记录 | 与本设计有关的部分 | 证据边界 |
| --- | --- | --- |
| [LosslessCut Smart Cut 跟踪 #126](https://github.com/mifi/lossless-cut/issues/126) | 功能仍包含多种素材和拼接问题，不能仅凭普通素材成功推断通用正确性 | 本次没有复现该 issue 中全部用户附件 |
| [MediaMolder PR #77](https://github.com/MediaMolder/mediamolder/pull/77) | 参数集与 NAL framing 是独立工程问题，不能只调整输出 codec 标签 | 本版采用 FFmpeg 的转换/承载接口，未移植该 PR |
| [avcut README 的限制](https://github.com/anyc/avcut/blob/7704c26c95a4540a43e5c9ce9c6470595a78eddc/README.md) | 作者提及伪影和容器测试限制，说明 GOP 局部编码概念成立不等于所有来源均可靠 | 不把这些历史报告当作当前代码的确定根因诊断 |

本次实验能证明下节明确构造的失败机制，不能替各 issue 宣布根因已确认或问题已修复。

### 7.1 素材矩阵

主矩阵每个源为 240 帧、192×112，包含移动图形、高频变化和显示帧号条码。素材由脚本生成，因此可以从源解码像素建立准确参照。

| 素材 | 需要覆盖的差异 |
| --- | --- |
| closed_b3_id0 | 闭合 GOP、B=3、源参数集 ID 0 |
| closed_b3_id3 | 同上，但源 ID 3，避免只测默认编号 |
| baseline | 无 B 帧、CAVLC、Baseline |
| open_gop | 普通关键帧之间存在跨 GOP 依赖，只有开头 IDR |
| mixed_open_idr | Open GOP 中定期插入真实 IDR |
| high10 | 10-bit 4:2:0 |
| multi_slice | 每帧 4 个 slice |
| ntsc | 30000/1001 帧率 |
| vfr | 不等显示间隔 |
| offset | 源时间戳整体偏移 2 秒 |
| fragmented | 分片 MP4 输入 |
| fullrange_sar | 全范围色彩、BT.709 标记、SAR=4:3 |
| nvenc | 实际 NVIDIA 硬件编码来源 |

每类都测试整片、IDR 对齐、两端非对齐、只改开头、只改结尾、单帧、跨 IDR 两帧、多段保留、相邻区间，以及一个 IDR 区间内的相邻区间合并；分别运行 avc3 和 stsd。

11 个拒绝测试包括空区间、越界、重叠、NaN 质量、无效模式、已有输出保护、输出等于输入、双视频轨、隔行、MPEG-4 Part 2，以及 High 4:4:4 Predictive 的无损源配置。补充测试另检查坏 NAL 长度的拒绝和临时输出清理。

### 7.2 验收依据

测试不使用 CLI 自己宣称的“成功”作为唯一依据：

1. FFmpeg 严格解码，要求退出成功且无错误日志。
2. 解码帧数、MP4 样本数、所选显示帧数一致；条码核对每个重编码画面的原始帧号。
3. 每帧 PTS 以有理数与预期精确比较；DTS 严格递增且不大于 PTS；总显示时长误差不超过 1 微秒。
4. 复制帧的解码 YUV 数组逐元素相同；独立读取 MP4 样本文件位置，计算各 VCL NAL 的 SHA-256 并比对。
5. 重编码帧的 YUV PSNR 必须大于 30 dB；最终普通 CRF=18 测试中的最小值为 **39.05 dB**。该数字仅描述这组素材，不是任意视频质量保证。
6. QP=0 回退输出的全部解码像素相同；检查色彩/SAR、单视频轨、sample entry、stsd 条目数。
7. 从两个输出模式的每个已声明同步样本 seek，后续解码帧哈希必须与线性解码相同。

画面比较参照的是**输入文件解码后像素**，不是最初生成 RGB 的未压缩画面；否则会混入源编码损失。

## 8. 能回答设计争议的实验

### 8.1 不改 ID 能否正常工作

最终矩阵中，源 ID 0 和源 ID 3 的所有普通导出均通过；本版新编码器使用默认 ID，既覆盖相同 ID 的定义切换，也覆盖不同 ID。两种 MP4 配置承载都成功。这说明改 ID 不是这个受约束方案的前提。

### 8.2 不恢复旧参数集会怎样

对一份正确的 avc3 混合输出，只把第一个复制 IDR 前的原 SPS/PPS 替换为等长 filler NAL，保持 MP4 样本大小和文件偏移不变。随后出现非法参考计数、错误重排序等解码日志和图像损坏。解码器在非严格模式下仍可返回 0。

这是一个有针对性的因果对照：同 ID 被新定义覆盖后，恢复原定义确实必要。它不证明“每个方案都必须带内插入 SPS/PPS”，因为 stsd 切换或不同 ID 共存还可以通过其他机制供给正确配置。

### 8.3 简单 FFmpeg 拼接为什么不够

实验还构造了一个 **LosslessCut 风格的简化命令配方，并非运行原版 LosslessCut 或逐行复刻其算法**：编码帧 13..23；从时间 0.96 秒开始复制到目标末端；再用 concat stream copy 拼接。

| 输入 | 预期输出 | 实际解码帧数 | 现象 |
| --- | ---: | ---: | --- |
| 闭合 GOP，8-bit | 214 | 216 | 预期复制画面都能对应，但额外多出 2 帧 |
| 闭合 GOP，10-bit | 214 | 216 | 同上；解码和复用均可返回成功 |
| Open GOP | 214 | 195 | 非单调 DTS 修补、参考错误、预期位置的复制画面不匹配 |

此对照只证明“几条朴素命令”没有自动解决全部边界问题，不能用作对 LosslessCut 当前版本的直接故障判决。其源码已有匹配时间基、边界减帧等补偿；本版用帧索引和两端规划取代这些按时间编排的启发式。

### 8.4 无损混合模式暴露了额外问题

早期测试曾将局部无损编码片段与原始有损 GOP 混合：

- 8-bit 输出在部分复制帧/边界帧出现像素不一致，尽管 VCL 字节未改、解码未必报错。
- 尝试新编码器使用不同 SPS ID，未消除该现象；单线程与不同 FFmpeg 解码版本的诊断也不足以排除问题。
- 10-bit 的 `CRF=0` 本身不能直接当成 QP=0 无损；必须明确使用 QP=0，并避免同时设置优先级更高的 CRF。

前两项的内部根因未完成定位。profile/transform-bypass 切换后的解码状态兼容性是合理怀疑，**不是已经证明的 FFmpeg 缺陷**。现有证据不足以宣称靠某个 SPS 字段补丁即可解决。

因此最终版本选择可验证的回退：请求 `--crf 0` 且存在编码边界时，整个选区都用 QP=0 编码。8-bit 与 10-bit、两种承载共 4 个用例全部逐像素相同；本来能全复制的剪辑不触发回退。CLI 同时给出提示和 JSON 标记，不把整段重编码隐藏成 Smart Copy。

x264 对高位深 CRF=0 与 QP=0 差异的说明见 [x264-devel](https://mailman.videolan.org/pipermail/x264-devel/2010-November/007918.html)；FFmpeg 封装的参数优先级见 [libx264.c](https://github.com/FFmpeg/FFmpeg/blob/n8.1/libavcodec/libx264.c#L1039-L1044)。

### 8.5 保守策略的代价

同样保留 `[13,227)`：

| 素材 | 输出帧 | 复制帧 | 编码帧 | 解码器实际返回帧 |
| --- | ---: | ---: | ---: | ---: |
| 闭合 GOP / 常规 IDR | 214 | 192 | 22 | 35 |
| Open GOP，只有开头 IDR | 214 | 0 | 214 | 227 |
| Open GOP，另有两个真实 IDR | 214 | 72 | 142 | 155 |

为输出边界画面，仍要从原 IDR 解码一些不保留的帧，因此解码帧数可以大于编码帧数。更细的参考依赖分析可以扩大复制范围，这是高级项目比本版复杂却有价值的地方。

## 9. 性能实测

1080p、30 fps、20 秒共 600 帧的 x264 源，保留 `[13,587)`：输出 574 帧，其中 480 帧复制、94 帧重编码，复制比例 83.6%。每种方案运行 3 次，计时包含进程启动、读取/索引、处理和 faststart；不包含素材生成与结果验证。

| 次数 | 本 CLI，秒 | 全选区 x264 medium CRF18，秒 |
| --- | ---: | ---: |
| 1 | 2.203 | 2.738 |
| 2 | 1.881 | 3.319 |
| 3 | 2.122 | 2.719 |
| 中位数 | **2.122** | **2.738** |

本次中位数约快 **1.29 倍**，不能据此声称数量级提速。CLI 边界编码/解码固定 4 线程，而命令行全编码使用自动线程；新旧 GOP 的压缩结构也不同，所以这是实际流程耗时对照，不是同线程、同码流、等质量的编码器基准。

高核心数机器上的短片会受编码器启动、线程分配、全片扫描和重写 moov 等成本影响。复制比例高并不等价于耗时按相同比例下降。本版主要实现并验证正确性，仍有合并相邻处理上下文、按任务规模选择线程数等优化空间。性能结果保留了全部三次数据。

## 10. 已解决的不足与剩余边界

### 10.1 本版已落实的改进

| 问题 | 处理 |
| --- | --- |
| I 帧、key flag 与安全接缝混淆 | 检查真实 IDR，保留完整依赖区间 |
| 首部精确但末端不精确 | 两端统一按显示帧求交与编码 |
| 新旧参数集定义混淆 | avc3 恢复或 stsd 切换，明确交给 muxer |
| AVCC 与 Annex B 混用 | 使用 FFmpeg BSF 和 muxer 转换 |
| VFR / B 帧导致时间估算误差 | PTS 精确索引、整数 tick、统一 DTS 计划 |
| “能解码”掩盖复制画面改变 | VCL 哈希、逐像素与帧号多重核验 |
| 无损混合模式不可靠 | 显式 QP=0 全选区回退，并保留失败证据 |
| 重复区间边界增加无谓编码 | 相邻保留区间先合并 |
| 临时输出和路径处理 | UTF-8 Windows 入口、临时文件成功改名、既有文件保护 |

### 10.2 仍然存在的限制

1. **不是最小重编码算法。** 长 Open GOP、非 IDR 随机访问点和更细粒度参考分析未实现。当前以扩大重编码范围解决正确性，不能说已达到这些项目的全部复制效率。
2. **输入支持面有边界。** 只接收固定格式、逐行 4:2:0 8/10-bit、首帧真实 IDR、完整时间戳的单视频轨 MP4，输入 profile 限于 Baseline / Main / High / High 10。High 4:4:4 Predictive 等无损源配置即使像素为 4:2:0 也拒绝，防止与新的有损边界混合。不支持隔行/MBAFF、4:2:2/4:4:4、动态分辨率、动态参数集、加密、多视频轨和部分复杂 edit list。
3. **不能把所有本程序混合输出再作为输入。** 它们可能包含动态带内参数集或多个 stsd；本版输入合同主动拒绝这些切换。再次剪辑应回到原始素材。后续需要为每个样本索引当前配置，按配置 epoch 解码与复制，不能只放宽检查。
4. **播放器互操作性未充分验证。** 已验证 FFmpeg 软件解码和 seek；没有验证 Windows Media Foundation、浏览器、VLC、硬件播放器全矩阵。NVENC 来源测试证明的是输入兼容性，不是输出硬件解码认证。
5. **附属信息不完整保留。** 基本色彩字段与 SAR 已验证；新编码帧清除源 side data。不保证任意 SEI、HRD、旋转矩阵、章节、timecode 或 HDR 元数据的完整保真。
6. **不负责坏流修复。** 样本格式和边界解码做了检查，复制部分不会全量解码；不构成对恶意/损坏 H.264 的完整验证器。
7. **工程规模与优化仍有限。** 单进程顺序处理，先扫描全片，内存索引随样本数增长；尚未设计索引缓存、长文件恢复、取消和 GUI。边界 B=0 在压缩效率上有取舍。
8. **测试代表性有限。** 主要为可复现合成素材与一种实际硬件编码器，尚缺相机、采集卡、广播和不同商用编码器的真实文件库。全部通过只对本报告的验收范围负责。

下一阶段最有价值的扩展依次是：动态配置输入及再次剪辑；真实素材/播放器回归库；非 IDR Open GOP 依赖分析；线程与重复解码优化。前两项应先于追求更少几帧重编码，因为它们直接影响实际使用范围。
