# h264 与 pipeline：效率潜力和验证覆盖对比

2026-10-28。比较仓库提交 `c1a5d14667b3d82e47a970c93c5efff1e25f9ae1`。本轮未修改两套实现；新增的基准脚本、日志、诊断样本和报告保存在本目录。

当前代码在本轮四组直接对照中均为 h264 耗时较低，pipeline 的中位耗时是它的 1.15～4.35 倍。两者充分优化后的差距不能由这些数字推算。两套普通有损剪切采用相同 IDR 决策，重编码帧数相同；区别主要是额外解码、数据搬运、进程和编码上下文的成本。

验证覆盖不等价。h264 的归档结果为 264 个导出、11 个拒绝用例、1 个参数集恢复消融和 5 个补充用例达到预期。pipeline README 记载另一 FFmpeg 构建下 165/165 通过；本轮统一使用 h264 的 FFmpeg 8.1.3 构建后，复跑结果为 148/165，17 项失败。已用独立 CLI 复现一个 VFR 时间轴错误，以及一个由 AAC 峰值降低触发的音频检测失败。

## 1. 本轮性能实测

使用同一台机器、同一个 FFmpeg 构建 `n8.1.3-24-g92611900bb-20261025`，1080p/30 fps 视频，无音频，默认 CRF18/medium。每个场景、每套实现各预热一次，随后交错计时三次，取中位数。计时包含进程启动、索引、处理和输出封装，不含验收。保留各自原来的线程设置：h264 固定 4 线程，pipeline 交给 FFmpeg/x264；这是当前实现整体性能对照，不是相同线程参数的编码器微基准。

| 场景 | 输出复制/重编码帧数 | h264 中位秒 | pipeline 中位秒 | pipeline / h264 |
|---|---:|---:|---:|---:|
| 20 秒源，两端非 IDR，保留 [13,587) | 480 / 94 | 2.230 | 4.239 | 1.90 |
| 20 秒源，保留 [60,540)，全部复制 | 480 / 0 | 0.676 | 2.936 | 4.35 |
| 60 秒源，保留靠后的 [1213,1787) | 480 / 94 | 3.461 | 6.770 | 1.96 |
| 20 秒源，五个不连续选区，每区间均只覆盖部分 IDR 区间 | 0 / 470 | 8.028 | 9.262 | 1.15 |

60 秒源由同一个 20 秒视频循环 stream copy 得到。五段分别为 [13,107)、[133,227)、[253,347)、[373,467)、[493,587)。各场景最后一次输出独立验证了样本数量、逐帧 PTS、DTS 单调且不大于 PTS、总显示时长（1 微秒容差）和严格软件解码，8 个输出全部通过。这些 CFR 检查不代替完整素材矩阵。

三次耗时有波动，尤其 60 秒场景 h264 为 3.461/5.838/3.307 秒，pipeline 为 6.770/11.105/6.352 秒。以上比值只描述这轮实际工作量，不是优化上限或所有视频的固定倍率。

原有两份报告不能直接以“比全重编快 1.29 倍”和“快 1.70 倍”比较实现优劣：它们的 FFmpeg 构建、全重编码对照参数和运行时状态不同。

## 2. 优化潜力

在相同输入、相同 IDR 策略、相同编码器与质量设置下，普通模式的复制比例相同。这一层优化潜力没有 C++/C# 的天然差别；若要减少长 Open GOP 的重编码范围，两者都需要更细的依赖分析或更多已证明安全的恢复点。h264 的 QP0 整选区回退是额外例外，不能将其与未经同等正确性验证的局部无损混合直接比较速度。

pipeline 当前主要额外工作包括：ffprobe 输出全部包的 JSON，再读取 NAL 建索引；全输入重封装为纯视频文件；每个编码段都用从文件开头运行、未提前终止的 select；各段落盘后再 concat；输出前还有一次文件复制。尤其对长视频或多个剪切点，重复全片解码远大于 C# 调用命令本身的开销。

pipeline 优先优化方向是：按已索引的 IDR seek 并限制边界解码范围；在符合 seek 语义的输入上省去全片视频预处理；减少中间文件复制与多余 mux；复用索引；对独立边界做有界并行。每一步都应重新验收显示帧号、时间基、片段时长和复制字节。直接依赖 concat 的默认片段时长已经在本轮 VFR 用例中失败，不能只追求命令更少。

h264 已具备按 IDR 局部解码和单 muxer 输出，进一步可减少连续复制段间的 BSF/配置重复工作、复用 packet 缓冲、缓存索引、按边界规模选择线程数，以及在保持 IDR 独立性的条件下减少编码上下文启动成本。

充分优化后的共同成本主要是：必要索引、保留压缩包的读写、边界依赖帧的解码、选中边界的编码和容器生成。编码占主导时，两者使用同样的 FFmpeg/x264，性能可以接近；复制占主导或大量小片段时，直接库调用通常更有利于降低固定开销。若 pipeline 保留多进程、多临时 MP4 的架构，其额外搬运与封装成本仍在；若改用持久化原生引擎，则执行架构已经逐渐接近 h264。

因此，优化后的 pipeline 可以超过当前未优化的 h264；两者都充分优化时，h264 路线通常更接近最低开销。没有完成相应实现和实测之前，不能给出“最大快多少倍”的数字。

## 3. h264 已归档的验证与 pipeline 覆盖

h264 完整矩阵本轮没有全部重跑；读取的是归档 JSON、脚本和报告。用于本轮对照的 h264 EXE SHA-256 与归档 build-manifest 完全相同，当前三份 C++ 源码也与该 manifest 一致。

13 类素材为：闭合 GOP/B=3/SPS ID0、ID3、Baseline/CAVLC、仅开头 IDR 的 Open GOP、Open GOP 中定期 IDR、High10、多 slice、30000/1001、VFR、时间戳偏移、分片 MP4、全范围色彩/SAR、NVENC 来源。10 种剪辑为整片、IDR 对齐、首尾非对齐、仅首端、仅尾端、单帧、跨 IDR 两帧、多选区、相邻区间和同 IDR 内相邻区间。

| 检查项 | h264 的验收及归档结果 | pipeline 现有验收 |
|---|---|---|
| 13 类素材 × 10 种剪辑 | avc3/stsd 两模式，260/260 | 同 130 种组合，仅 avc3；本轮 125/130 |
| 严格软件解码 | 必须成功且无错误日志 | 有对应检查 |
| 帧数 | 解码帧数、样本数、期望帧数三者一致 | 主要断言样本数；未单独断言解码帧总数 |
| 显示 PTS | 每帧以有理数精确比较 | 有逐样本显示时间检查；本轮 5 个视频 VFR 用例失败 |
| DTS | 输出 DTS 严格递增、DTS ≤ PTS | 既有套件未独立断言输出 DTS；输入检查不等价。本轮四个 CFR 性能输出额外通过 |
| 总显示时长 | 实际输出 duration 与计划差 ≤ 1 微秒 | 比较计划计数不等价于检查实际输出总时长；本轮四个 CFR 性能输出额外通过 |
| 复制画面 | YUV 数组逐元素相同 | 源/输出同位置 framemd5 相同 |
| 压缩视频确实原样复制 | VCL NAL SHA-256 对位比对 | 未做 VCL 字节哈希 |
| 重编码画面身份/顺序 | 每帧画面条码检查；包括复制和重编码帧 | 没有独立条码断言 |
| 重编码质量 | 每帧 PSNR >30 dB；归档最低 39.049 dB | 每个编码区间平均 PSNR 的最小值；非每帧下限，且取值失败返回 null 不会使验收失败 |
| 无损回退 | 8/10-bit × 2 承载，共 4/4；逐像素一致 | 未覆盖；无对应整选区 QP0 回退 |
| MP4 sample entry / stsd | 检查 avc3/avc1 标签及多 sample description | 未独立检查；没有 stsd 路线 |
| 色彩/SAR | 有 | 有 |
| 从同步样本随机 seek | 两种输出模式各一个专项，从示例文件所有已声明同步样本 seek，比对后续帧哈希 | README 有“已验证 seek”文字，但当前测试源码/随仓证据未找到对应专项，不能计为同等覆盖 |
| 参数集恢复消融 | 删除首个复制 IDR 前原 SPS/PPS，确实检出损坏，1/1 | 未做 |
| 拒绝/异常输入 | 11/11；另有坏 NAL 与失败输出清理专项 | 3 个端到端负例：其他编码、多视频轨、既有输出；非法范围另有逻辑检查，未覆盖全部 h264 负例 |
| 中文路径、音频轨在前但丢弃 | 两种承载都通过 | 未找到同等专项；有另外的保留音频测试 |
| 音频 | 不处理 | 4 种变体 × 6 剪辑，共 24；本轮 12/24 |

上述“未覆盖”表示当前测试没有同等证据，不表示对应功能一定失败。两者都未完成广泛的真实相机/广播素材、Media Foundation/浏览器/VLC/硬件解码器互操作矩阵或完整 HRD/CPB 合规验证。NVENC 来源是编码输入覆盖，不代表硬件解码验证。

## 4. pipeline 本轮复跑与最小诊断

| 类别 | 通过 | 失败 | 总数 |
|---|---:|---:|---:|
| 视频矩阵 | 125 | 5 | 130 |
| 音频 | 12 | 12 | 24 |
| 负例 | 3 | 0 | 3 |
| 逻辑 | 8 | 0 | 8 |
| 合计 | 148 | 17 | 165 |

运行器把 InvalidKeepRangesAreRejected 的数据行作为一个结果报告，所以实际统计与 README 的 165 一致，不能将手工展开数据行所得的 169 当作测试运行器计数。

5 个视频失败全部属于 VFR：cross_idr、multiple、head_only、tail_only、both_edges；另有 4 个带音频的 VFR 用例因相同视频时间戳检查失败。8 个音频用例则因检测到的脉冲比预期少一个而失败。

**VFR 最小案例：** source-vfr.mp4 保留 [23,25)。源两帧对应的相对 PTS 应为 0/0.08 秒，h264 输出正确；pipeline 输出为 0/0.04 秒，总时长也由预期 0.12 秒变为 0.08 秒。保留下来的第一个临时单帧 MP4 已将该帧 duration 写成 0.04 秒，concat 再按此时长连接后段。因此问题在编码段的帧时长表达及后续拼接，并非剪切计划选择了不同帧。

**音频最小案例：** 单轨 AAC、closed_b3_id0、保留整片 [0,240)。输入输出均解码为 460800 个单声道采样。首个脉冲依然存在，但局部峰值由 0.9262 降为 0.5108，低于源全局峰值一半形成的阈值 0.5547，导致算法报 59 个而不是 60 个脉冲。该例证明脉冲计数失败不能直接等同于丢音频样本或裁剪偏移；其余计数失败没有逐个完成同样诊断。音频检测应进一步区分时间对齐错误与有损编码导致的波形/峰值变化。

本轮使用的 FFmpeg 与 pipeline README 的 `git-2026-10-24-d8990137ee` 不同，因此本次结果不能证明其历史记录虚假；它表明原通过结论不能直接推广到 h264 当前使用的 FFmpeg 构建。失败已经通过独立 CLI 复现，不只是测试运行器报告异常。
